# Phantom-animate architecture

Implements `animation-goals`. This is the architecture of **layout mode**: the program stages a scene out of simple shapes and renders a playblast that a neural network turns into the final frame. The user confirmed external FFmpeg, GPU rendering, and our own set of builtin shapes.

The document describes the architecture and the status. A major shift from the previous version: the program is **no longer an animation tool**. A character is a pose, not a performance: procedural actions, imported clips, retargeting, takes, live control and "on twos" mode are gone from the program, and this text describes a world without them.

## Technical foundation

- **Bevy + bevy_egui**: scene, skinning, materials and render-to-texture from Bevy; the editor on egui. We do not build our own 3D engine on top of bare wgpu. Bevy 0.17.3 is verified by a build and headless rendering on Vulkan (see "Implementation status"); bevy_egui 0.38.0 and egui 0.33 are not integrated yet and are not verified by a build. Versions are pinned in Cargo.lock.
- **ufbx**: FBX and OBJ through our own adapter into the project format (crate ufbx 0.4). The Rust bindings use a C library, so a Rust application does not mean an all-Rust dependency tree. ufbx provides skinning and animation APIs, but no ready-made Bevy importer and no automatic retargeting.
- **FFmpeg/ffprobe as separate processes**: video/audio decoding, normalizing audio to a common format, and encoding MP4/H.264 + AAC. PNG and still images use the Rust image crate; audio output uses cpal. Availability and compatibility of image/cpal/rmcp are not verified by a build yet.
- **serde/JSON**: versioned project document; **rmcp** as the candidate SDK for MCP stdio. The local connection to the open app is a Unix domain socket, not a public TCP server.

Three domain Rust crates are enough: `core`, `runtime`, `app`. We do not create a crate per button or subsystem; the parts described below are internal modules. Desktop and headless are modes of one application. Network services, plugins and distributed rendering are not needed.

## Data ownership and dependencies

**core** owns the project document, commands, undo history, time, poses, scene state evaluation and audio mixing. It does not depend on Bevy, egui, MCP, the GPU or the windowing system. Document identifiers are stable and are not Bevy Entity IDs. The project stores scenes with a stage, Phantoms, skeletons, asset references, position keys, cameras, drawings, and the film's sequence of scenes and clips.

**runtime** depends on core and implements file storage, import, FFmpeg, audio playback, the GPU representation of the scene, and export jobs. The Bevy World is a derived representation, not an alternative home for the project. GPU resources and transient media buffers are not serialized. A missing GPU does not block editing commands; a renderer is created only when an image is needed.

**app** depends on core/runtime and contains egui, MCP and the local bridge. Both surfaces call one dispatcher of typed commands, state queries and jobs. The UI never mutates the document directly, and MCP does not emulate keystrokes in order to set frames and poses precisely.

Dependencies point `app → runtime → core`; app also uses core types. One session owner applies changes sequentially. Background jobs work against a revision snapshot; the result of a stale job never replaces newer data.

## Commands and MCP

Commands cover creating/opening/saving a project, scenes and the stage, assets, Phantoms and poses, position keys, camera, strokes/painting, editing/audio, baking and export. Queries return the current revision, properties, time ranges and job results. The exact tool catalog is defined by the implementation of these operations, not by a separate feature set for the agent.

Every command validates IDs, types, number finiteness, ranges and asset availability before making a change. A change is atomic and has one undo step; a brush stroke is a whole operation, not thousands of separate undos. MCP action recording sets times explicitly and does not depend on how fast requests are delivered. Long-running import, bake and export return a job ID and progress, report errors, and support cancellation.

MCP responses follow one uniform machine-readable contract, with no legacy text-JSON fallback. Success carries the operation-specific object directly in `structuredContent` (no artificial `data` wrapper); the regular `content` is empty. Every successful document mutation is centrally augmented with post-command `revision`, `next_id` and a canonical compact `entity` (type, stable IDs and current fields; deletion is `removed: true`), so the agent needs no follow-up `scene_get`. The snapshot is built from the already-mutated `Project`, and one user mutation corresponds to one revision and one undo step; `history_undo`/`history_redo` return the current revision and `{kind: history, operation, applied}`. Operations are classified explicitly: creating/opening/saving a project and locking are lifecycle, and queries plus render/job are not document mutations and do not get `revision`/`next_id`/`entity`. A tool error carries `isError: true` and `structuredContent: {code, message, details}`; the stable snake_case `code` and the `details` fields come from a typed error variant, not from parsing a localized `message`. Text content never contains serialized JSON. Local parameter errors use the code `invalid_input`; state, IDs, paths and lock owners are passed in `details`. Standalone and the GUI bridge use one MCP-envelope helper. The internal newline-JSON bridge returns either a structured `result` or `error_data` of the same shape and has no string `error` field.

Render job diagnostics: the child process's stderr is collected by an asynchronous stream into a bounded ring buffer (the last ~64 lines / ~8 KiB) while stdout stays a clean progress protocol; `job_status` returns completion, exit code, parsed progress (frames_done/total), elapsed time and the stderr tail, and `job_list` returns the status of every job in the session. Committing completion joins both pipe readers (stdout and stderr reach EOF after the child exits) and drains the progress channel once more, so the last progress line and the stderr tail are guaranteed to land in the status instead of being lost to a race with the reader threads. State queries are augmented with snapshots: `scene_get` returns a full serde snapshot of the scene, `asset_list` returns assets (id/kind/path). `render_still` renders one PNG frame inside the session owner and is available both standalone and through the bridge; the MCP response contains one image block and a `structuredContent` with `scene/frame/camera/width/height/mime_type`, but does not duplicate the base64 PNG in the metadata. The operation requires a GPU and validates dimensions (<= 4096) before touching the device; errors use the shared structured envelope. The `report: true` option (corrective C3.2 — the agent's "eyes") adds pure frame metrics to `structuredContent` without re-decoding the PNG: `mean_luma`/`luma_p5`/`luma_p95` (Rec.709, opaque pixels only), `empty_coverage` (the fraction of the frame with alpha == 0, i.e. no geometry — the same method as in the A3 measurement), `objects_in_frame`/`objects_total` (a Bevy visibility fact: an object counts if at least one of its Mesh3d parts passed the selected camera's visibility; this is not a background alpha heuristic), and the non-cryptographic `scene_digest` (64-bit hex of the canonical serde scene snapshot; it changes on any change to the scene document). The MCP tool renders 1024x576 by default and a cheap 480x270 preview with `report: true`; the metrics are computed by `phantom_runtime::render::metrics::frame_metrics` over the RGBA readback, so they are deterministically testable without a GPU and are equally available standalone and through the bridge.

Getter queries (corrective C3/D2–D4): `camera_get {scene?, camera}` — a full canonical camera snapshot (id, name, range, camera with its keys and focal_mm, and the attachment) plus the active camera and the parent scene's id and current revision; `asset_get {asset}` — the canonical asset (id, kind, relative path, `exists` — a file at that path inside the project directory) and cheap usage references (the scene background and video background, objects, the Phantom's imported rig, and the audio clips of scenes and the film); a nonexistent id yields the stable `not_found` with `nearest_ids` (up to 5 closest existing ids by numeric distance) in `details`. `film_get` returns the film's ordered clips and the mapped total length in frames at 24 fps and in seconds. Getters are pure queries: they do not bump the revision, do not create undo steps, and do not get the mutation acknowledgement `revision`/`next_id`/`entity`; where applicable their values include the current project revision. `project_recent` returns the last successfully created/opened project directory even after the process died, plus the current directory, revision and active scene of this MCP session; it works with no project open. Persistence of the "last project": after a successful `project_new`/`project_open`, the path and a unix time are written atomically (temp file + rename) to per-user state at `$XDG_STATE_HOME/phantom-animate/recent.json`, falling back to `~/.local/state`; only the path and timestamp are stored, never lock tokens. A corrupt or unreadable file produces a warning (`recent_state_corrupt`/`recent_state_unreadable`) and an empty answer but does not prevent the server from starting; a successful project open rewrites the file. The state path is injected into `Session` for deterministic tests (no mutation of global environment and no test touching the real user file).

`batch {ops}` is an atomic package of document mutations (corrective C3.8): operations in wire format carrying an `op` tag are executed sequentially by the regular Session dispatcher (the same validation and the same deterministic id allocation as single calls — scene→phantom→key chains work inside one package), but each operation's class is checked up front: only document mutations are allowed, and nested batches, queries, lifecycle and render/job are rejected before any document changes (`invalid_input` with `index`). If any operation fails, the project and history are restored from a deep snapshot — no partial state, no extra undo steps and no spent ids remain; the `batch_failed` error carries `index`, the operation name, the inner `code`/`cause` and `rolled_back: true`. On success the package's undo steps are collapsed into a single `Command::Batch` step (`History::squash_last`) and the revision is normalized to +1 for the whole package; the acknowledgement is `applied`, `results` (per-op created ids and canonical `entity`, without intermediate revision/next_id), plus the final `revision`/`next_id`/`entity` of the last operation. Undo rolls back the whole package in one step and redo reapplies it with the same ids. The core `Command::Batch` provides the same atomicity for direct application: commands are executed against a draft document and the document is left unchanged on error; an empty and a nested batch are `InvalidBatch`. The MCP `batch` tool takes an array of JSON operations and substitutes the connection's active scene into operations without a `scene` field; unlike the single convenience tools, wire-format angles are radians and audio is samples at 48 kHz (this is documented in the `ops` field description and in the server instructions).

Effects and post-processing (corrective B3): `scene.grade: Option<SceneGrade>` — frame color grading through Bevy's `ColorGrading` (exposure EV, temperature/tint, hue, post_saturation plus saturation/contrast/gamma/gain/lift sections; LUTs are not supported); `scene.fog: Option<SceneFog>` — exponential `DistanceFog` (color + density > 0). `scene.vfx: Vec<SceneVfx>`: `particles` — a deterministic hash simulation (splitmix32 by particle index, no RNG state: a frame does not depend on render order; cap of 1024 quads; unlit alpha-blend, Y-billboard toward the camera, sin fade at the ends of a particle's life) and `water` — a plane with a normal map (asset) and UV scroll via `uv_transform` over time; presets `snow|embers|smoke|rain` (gravity < 0 — falling, > 0 — rising); `keys: Vec<VfxKey>` — enabled/density steps keyed off elapsed time; `attach` — an emitter on a bone (B2). The `SetGrade`/`SetFog`/`AddVfx`/`RemoveVfx`/`SetVfxKey`/`RemoveVfxKey` commands validate before mutating; MCP `grade_set`/`fog_set`/`vfx_add`/`vfx_remove`/`vfx_key_set`/`vfx_key_remove`. Bloom/vignette/depth_of_field/god_rays are deliberately deferred: the available set of Bevy 0.17.3 crates has no camera components for them (verified against the registry sources), and god_rays needs a custom shader.

Materials (corrective B4): `Phantom.material_patches`/`SceneObject.material_patches: Vec<MaterialPatch>` — patches (target by mesh-part material name or all; base_color sRGB, metallic, roughness, emissive linear > 1 allowed, opacity < 1 enables alpha blend, unlit) on top of the asset's imported materials: the asset is not mutated and undo is one step. `material_preset`: matte | skin | metal | wet | glass | glow — names beat bare numbers. The `SetMaterialPatches` command (exactly one owner, range validation before mutating); MCP `material_set` (preset + explicit fields override it, clear removes it) and `material_list` (the model's mesh parts: current import values and effective values after patches; builtin actors without file IO). Rendering: a patched material is a clone of the asset when the target matches, and the model fill cache is not broken; spawning actors and props goes through one `apply_material_patches` path.

Attachments (corrective B2): `SceneObject.attach`/`SceneLightSource.attach: Option<Attachment>` (phantom + bone name + offset in bone space, radians) — the transform is recomputed from the pose every frame: world = Phantom root (position + yaw + `phantom.scale`) ⋅ accumulated bone hierarchy (`rig::accumulate_bones`, topological order; builtin — `rig::actor_bones`, imported rigs — SkinData, the hierarchy has been stored in PhantomEntities since forge) ⋅ offset; the bone name is matched case-insensitively. An attached object's own transform keys are not applied (the key's scale is inherited on top of the actor's scale); for an attached light source the intensity/enabled keys do apply, the transform ones do not. The `AttachObject`/`AttachLight` (None — detach) and `SetPhantomScale` (finite > 0) commands validate that the phantom exists and the bone name is non-empty before mutating; MCP `attach` — one shape: object | light | prop (creates an object from an asset and attaches it in one call — "a flashlight in the hand"), `detach: true` detaches; `phantom_scale_set`. The actor's scale (`phantom.scale`, serde default 1.0) is applied to the root entity. Forge tests without a GPU: the object follows the bone across frames, and scale lands on the root.

Scene staging (corrective B1/B5): the scene stores `lights: Vec<SceneLightSource>` — document light sources point (lumens) / spot (lumens + cone in radians) / directional (lux) with a name, color, on/off, opt-in `shadows`, and `LightKey` keys (pose + optional intensity/enabled on a frame). `SceneLightSource::at(frame)` — one semantics: with no keys and before the first key — the `rest` pose; between keys, linear interpolation of the transform and of the EFFECTIVE intensity (None inherits the source's body value), yaw along the shortest arc, enabled a step from the last elapsed key (the future never looks into the present). The `AddLight`/`RemoveLight`/`SetLightKey`/`RemoveLightKey` commands validate (cone in (0,π), finiteness) before mutating and undo in one step; MCP `light_add`/`light_remove`/`light_key_set`/`light_key_remove` take degrees. `scene.ambient` (`AmbientMode::FromBackground|Fixed|Off`, serde default from_background — the previous behavior) separates ambient from the background: fixed/off are set at forge and are not overwritten by a video background. `scene.sky` (B5, linear RGB) — a clean frame color: the camera's clear color instead of transparency, which makes the frame opaque; MCP `scene_ambient_set`/`scene_sky_set`, commands `SetAmbient`/`SetSky`. Forge and `apply_scene_frame` spawn and animate the sources without rebuilding the world (LiveSync rebuilds on a revision change); forge tests without a GPU cover spawning (cone/lumens/shadows), per-frame key application, and the ambient/sky modes.

Audio pipeline (corrective A4/A6/B6): `AudioClip` has `fade_in_samples`/`fade_out_samples` (serde default 0 — old projects have no fades) and the mixer applies a raised-cosine (equal-power) gain per sample; the `UpdateAudioClip` command is a targeted patch of offset/len/fades with validation before mutating (a fade is no longer than the clip, len > 0; `AudioClipNotFound` is a stable `not_found`). MCP: `audio_clip_add` takes `fade_in_secs`/`fade_out_secs`, `audio_clip_update` takes a partial patch in seconds; CLI: `clip-add --offset-secs/--len-secs/--fade-in-secs/--fade-out-secs` (mutually exclusive with the sample forms) and `clip-update`. Peak normalization of the mix is a deliberate opt-in: `FilmExportOptions.normalize` (default false) with `target_peak_dbfs` (default −1.0) scales the whole mix by a single linear coefficient from the peak, `mix_film` still returns the peak and it is now used; CLI `render-film --normalize --target-peak-db`, MCP `render_film` — `normalize`/`target_peak_db`. `phantom-animate render-audio` mixes the film to WAV without rendering video (a preview of the mix). Loudness metrics are RMS/peak dBFS (audio_report), not K-weighted LUFS; ducking, a limiter and SFX track types are deliberately deferred. The background `zone_averages` are averaged with alpha weighting (A7): a semi-transparent PNG no longer drags ambient to black, and a fully transparent zone is a neutral 0.

`audio_report {scene?}` (corrective C3.4/A4) is a checkable fact about sound before rendering: track and clip durations in seconds against the length of the scene/film, RMS and peak dBFS of the fragments actually used (offset..offset+len; the "near silence" threshold is −60 dB — the case of a track's quiet intro), and warnings `audio_beyond_video`/`audio_beyond_source`/`quiet_fragment`/`audio_longer_than_video`/`decode_failed`. Decoding is lazy, once per unique (asset, offset, len), through ffmpeg (`ffmpeg_available` — a cheap `ffmpeg -version` run); without ffmpeg or without a project directory the report degrades to document data with the `ffmpeg_unavailable` warning, and a decode error for one asset is a per-clip `decode_error` — the report does not fail. The operation is a Query (no revision/entity). `state_get` additionally carries `audio_summary` (video/audio/lost_seconds per scene and for the film) from pure document data without decoding. `film_add` returns `warnings` with `audio_longer_than_clip` when the edit range is shorter than the scene's longest audio track.

`job_wait {job, timeout_secs}` blocks the call until the job finishes or the timeout expires, then returns the same shape as `job_status` plus `timed_out` (true only when the timeout expired while the child process was still alive; no cancellation is implied). `timeout_secs` must be finite and within 0..=300, otherwise `invalid_input` before the first poll; waiting is a poll with a pause ≤ 20 ms, no busy-spin; completion observed inside the wait finalizes the exit code and the stderr tail through the same path as `job_status`, and a zero timeout validates the id and returns the status immediately. The operation lives in the shared Session/Op dispatcher, so the bridge gets it without a separate implementation; the bridge connection is held until it returns. `describe {tool}` returns the name, description, inputSchema, outputSchema and notes on units/usage, generated from the same ToolRouter metadata as `tools/list` — one source of schemas, no manual duplication, and drift between `describe` and `tools/list` is excluded by a test; an unknown tool gives the stable `not_found` with `nearest_tools` (up to 5 closest registered names).

Pure document diagnostics (corrective C3.1/C3.3, no render and no GPU) live in `app/analysis.rs` and share formulas with the renderer: the vertical FOV has a single source, `phantom_core::vertical_fov` (`2·atan(12/focal_mm)`, a sensor 24 mm high), used by both render sites (`forge` and the per-frame update) and by diagnostics; the horizontal FOV is derived from it through `phantom_core::horizontal_fov` with the aspect ratio (the MCP parameter `aspect`, 16:9 by default). The camera for diagnostics is `Camera::sample` plus the same basis as in the renderer (`YXZ(yaw, pitch)`, looking down local −Z), and the screen is the same geometry that `mesh_gen::screen_mesh` builds. Three Session operations of class Query (they do not bump the revision, no `entity`/`next_id`, no undo steps) and same-named MCP tools with documented fields (degrees out, frames at 24 fps in): `validate {scene?}` runs the invariants — stage geometry (`invalid_stage`) and the footprint leaving the scene boundary (`out_of_stage`, error; commands clamp, so a finding means a document written by hand or before the stage existed), screen geometry (`bg_geometry_invalid`, error), FOV coverage at the keys of every scene camera (`screen_fov_gap`, warning; suggested_fix names the needed width in meters or the limiting focal_mm), a camera looking away from the scene (`camera_faces_away`, warning — a command refuses such a key, so a finding means a hand-written document, and cameras without keys are not judged), an attachment to a subject that disappeared (`camera_subject_missing`, warning), motion coverage holes (`motion_gap` — the keys do not cover the whole scene range), audio clips outside their owner's range and track lengths (`audio_out_of_range`/`audio_length_mismatch`, frames + seconds), edit clips outside the scene or outside their camera's own range (`film_clip_out_of_scene`, error), missing asset files (`asset_missing`, error; relative to the project directory), film assembly checks (`camera_not_in_film` — a named camera not assembled when the edit references cameras at all; `film_coverage_gap` — scene frames never shown; `film_overlap` — some frames shown twice; all warning), a phantom without motion and an empty scene (info). The response is `{ok, revision, findings:[{code, severity, where, why, suggested_fix}]}`; ok=false only for error-severity; finding order is deterministic (scene, code, frame; project-level findings first); with no `scene` and no active scene — the whole project. `camera_coverage {scene?, frame?, camera?, aspect?}` returns `camera_id` (or null — the scene's own camera), the camera pose and FOV in degrees under the `camera` key, the azimuthal/vertical screen span seen from the camera, the gaps `gap_deg` per side, and a point `in_frame` test for each phantom/object; the default frame is the start of the camera's range; with no background, `background: null` plus the finding `background_absent`. `background_fit {..., margin_deg?, camera?}` (default margin 5°) without `camera` computes over the WHOLE scene (corrective_2 K0.1): it samples the keys of every scene camera, and the size must cover every sample — that is, the union of their requirements, not one camera (a camera looking elsewhere would otherwise leave a hole in its own frame). The response carries `scope` (`scene`|`camera`), the `camera_count`/`samples` counters, `cameras[]` with each camera's worst frame (`covers_current`, `gap_deg`, `needed_width_m`) and the top-level camera of the binding sample, plus `suggested {width, height, center}`, `panorama_aspect = width/height` for the panorama generator, `size_covers` (false — size cannot help, the screen has to be moved), `current`/`delta` and `fits`. An explicit `frame` without `camera` is `invalid_input`, not silently ignored: each camera has its own range. The approximations are fixed in the module document: coverage is estimated from 129 columns of the flat screen and two edges in height (sampling error < width/128 m), vertical coverage from the worst column inside the frustum (conservative), screen points behind the camera are excluded from the span, and the point test uses the root point without model volume. Fitting goes per axis: width — growth to the covering boundary and a bisection (the span is monotone in width), then height once the width already suffices (otherwise no column lands in the frame); `center` is preserved; results are rounded up to 0.01 m and do close the frame — fixed by a fit→coverage roundtrip test and by a scenario test covering two opposite cameras. `camera_report {scene?, camera, every?, width?, height?}` (corrective_2 K0.2) gives the agent "eyes" on a camera's whole stretch rather than one frame: it renders a sample of its frames with a single renderer (without `every` — up to 5 evenly spaced points including both ends; with `every` — every Nth frame, hard limit 12 frames so the report does not become a render of the whole range) and returns `rows[{frame, mean_luma, luma_p5/p95, empty_coverage, objects_in_frame}]`, `aggregate` (mean/min/max brightness, maximum emptiness, how many objects are visible) and `findings` (`empty_frame`, `camera_empty`, `objects_out_of_frame`). It is a Job-class operation, without `revision`/`entity`; dimensions/references are validated before touching the GPU. A preview of the whole film is the CLI `render-film --preview --every N`: the same clip→scene mapping and clip camera as the export, but into a PNG contact sheet (480x270 by default), without MP4 and without sound. The tools are mentioned in the server instructions and in `studio_capabilities.features.pure_diagnostics` (for pure queries); bridge parity comes from the shared Session Op, with no separate implementation.

A whole-scene review sheet (`look`, Job class) is the agent's eyes on the staging rather than one frame: it renders several directions around the scene at one frame (`mode: angles`) or a strip of frames through one camera (`mode: frames`) and tiles them into **one** contact sheet (one image block; the base64 is not duplicated in the metadata). Every tile carries `mean_luma`/`luma_p5`/`luma_p95`/`empty_coverage`/`objects_in_frame`, and the response carries each tile's direction and frame, the sheet's size, a digest of the staging, and a `look_empty` finding when no tile shows any geometry (a partly empty tile is not a defect: a review frame legitimately consists of background). The target is actor/object names or `phantom:<id>`/`object:<id>`, by default everything staged, and on an empty scene the stage box itself; an unknown name is `not_found` with the existing names. Directions are `front|back|left|right|top|three_quarter` or an explicit `[x,y,z]`; the default distance is derived from the target's size, the lens and the aspect ratio (the target is treated as its bounding sphere, so every tile is shot from the same distance and the tiles stay comparable). Limits: at most 12 tiles, tile side and sheet long side 4096. The pure part lives in `core/view.rs` (`LookView`, `fit_distance`, `camera_looking_at`, `TargetBox`) and is tested without a GPU, including a check that the fitted distance really does contain the target; the review camera is substituted into a copy of the scene, so runtime is untouched. Every argument error (`mode`, view name, zero direction, unknown target, size, unknown camera) is raised before the GPU comes up. The CLI `look` writes the sheet to a PNG and prints the tile metrics.

In windowed mode the MCP bridge connects to the owner of the open project. In standalone mode stdio creates a separate session without a window; logs go to stderr and stdout carries only the protocol. The socket lives in a private runtime directory of the user with restricted permissions. File access is limited to allowed roots; canonical paths, symlinks and escaping a root are checked. Loading external textures does not give the importer unlimited filesystem access.

The MCP server keeps a navigational `active_scene` separately for each stdio server/bridge connection: creating a scene selects it, opening/creating a project selects the first scene or `null`, and the disappearance of the selected scene selects the nearest remaining stable ID (the smaller one on a tie) or `null`. `scene_select` is the only explicit scene operation that changes the selection; other tools take an optional `scene` and, when it is omitted, resolve it at the MCP boundary or return the stable `no_active_scene`. The Session `Op` still requires a scene ID and does not own MCP navigation. `state_get` is augmented with `active_scene` and `allowed_root`. `studio_capabilities`, without a GPU probe, reports the contract/protocol versions, standalone/bridge, root, platform, the fixed 24 fps/48 kHz, limits and features; the GPU stays `unknown_until_render`.

MCP schemas describe every field (units, range, semantics) and tools/list always carries an object `outputSchema`; `structuredContent` stays authoritative. At the MCP boundary angles are named `*_deg` and converted to core radians, audio is given in seconds and converted to 48 kHz samples, and motion uses typed objects instead of tuples or a parallel yaw. `key_set` preserves omitted components from the exact key or from the evaluated state by default, and lights update with patch semantics. Drawing normalizes `canvas|screen|ndc` to a canonical 1920×1080 canvas. `render_scene.out` defaults to `<project>/frames`, and the render range is a typed `[start,end)` with end exclusive.

One project is never written by two sessions at once: a writer lock, and a second process either connects to the existing session or opens a separate copy. There is no live recording in the program, so the bridge has no "busy" mode either.

## Time, timeline and poses

Edit timing is whole frames at 24 fps; audio is normalized to 48 kHz, that is 2000 samples per frame. Lengths and trims are half-open ranges `[start, end)`. Source video timing is read from timestamps rather than assumed to be a constant FPS. Playback with sound syncs to the audio clock, and to the monotonic clock without a device; preview may drop displayed frames under load. Offline export computes each frame's concrete time independently of wall clock and GPU load.

**A character is not animated.** A Phantom's state at a frame is a pure function `evaluate(phantom, range, frame)`: position and `yaw` rotation are interpolated between keys and held outside them, while the **pose is taken from the key in force and switches on its frame**. There is nothing to blend a pose with: a pose is what was staged, not what is performed. Before the first key the value holds rather than extrapolating backwards.

A pose is named and static: `ActorPose { Stand, Sit, Lie }` in the key instead of the former action. The pose set is declared by the actor's species (`BuiltinActor::poses`): the human and the wolf hold all three, the horse stand and lie, the bird stand and sit. An unavailable pose is the `unsupported_pose` error with `{actor, pose}`, not an approximate substitution. An imported rig has no poses: it renders in bind pose, and the pose field in a key is ignored for it.

Implemented: `MotionKey { frame, position, pose, yaw }` (serde default of the pose is `Stand`, so an old manifest with `action` loads and the action itself is discarded); `rig::sample_actor_pose(actor, pose)` with no time, so "local action time" is gone from frame evaluation; `RigRef::validate_pose` checks the pose before mutating in every command that sets a key. Surfaces: CLI `set-key --pose`, MCP `key_set`/`motion_replace` with `pose`, the pose combo in the GUI timeline, `builtin_catalog` returns poses by species and the default pose.

Deleted along with the animation: `core/clips.rs`, `core/retarget.rs`, `core/control.rs`, `Take`/`TakeId`, `ClipUse`/`ClipUseId`, `RetargetProfile`, the `Phantom.clip`/`clip_track`/`takes`/`active_take` fields, the clip and take commands, "on twos" mode (`time::on_twos` and the `twos` flag), clip loading and sampling in runtime (`ClipData`, `load_clip`, `load_clip_retarget`, `list_stacks`, the clip cache and bone→track maps), live control and recording in the GUI, the `take_*`/`phantom_clip_set`/`clip_use_remove`/`clip_list` MCP tools and `set-clip` in the CLI. `AssetKind::MotionFbx` stays in the enum as a legacy variant: without it an old manifest does not deserialize, but no path produces or consumes it any more.

The stage volume does not inherit the character's movement; the floor constraint applies to the reference point and is not a collision simulation of the whole model.

## Scene stage (layout mode)

A scene is a floor at `y = 0` and an **invisible bounding box**: the floor is configured separately (`floor`), while the box defines where the staging may stand at all. `core/src/stage.rs` holds `StagePreset` (small 10×10×4, medium 30×20×8, large 80×60×20 m — width × depth × height), `StageSize`, `Stage { preset, size, center }` and `Footprint` — the local footprint of an entity (half-extents plus the center offset from the origin). `Scene.stage` has a serde default of "medium scene", so an old manifest loads without migration.

The clamp is performed by the **core**, not by the MCP boundary: otherwise the GUI and the CLI would remain a hole, and undo would keep a coordinate that does not exist on the scene. `Stage::clamp(position, footprint, rotation)` computes the world AABB of the box under rotation (`|R| · half`, exact for any orientation) and clamps per axis; a box taller than the stage stands on the floor and passes through the ceiling, and horizontally it is centered. The clamp is applied in the `SetMotionKey`, `ReplaceMotion`, `SetObjectKey`, `ReplaceObjectMotion`, `AddBuiltinObject`, `SetPhantomScale` commands and in the new `SetStage` (changing the stage recomputes everything already staged in one undo step). `CommandOutput` carries `clamped: Vec<Clamp>`, and the session acknowledgement gateway adds `clamped: true` and `clamps[]` with the coordinates before and after to the response — the agent sees that it was corrected.

The footprint comes from the tables that already exist: `BuiltinActor::footprint(pose)` (the pose changes the space taken: a lying figure is long and low), `catalog::CatalogEntry::footprint()` for catalog items and `Asset.bounds` — half-extents that model import computes once and writes into the manifest; a model with no recorded footprint is clamped by its reference point. `phantom.scale` and `object.key.scale` multiply the footprint.

Surfaces: MCP `stage_set`/`stage_get`, CLI `set-stage`/`stage`, the "Stage" panel in the GUI, `state_get.stages`, `builtin_catalog.stage_presets` and `studio_capabilities.features.stage`. Cameras are not subject to the clamp: they live outside the stage and look into it.

## Scene objects (props)

An object is a static (non-skinned) placement of an imported OBJ/FBX model in the scene, not an animatable character: no actions or skeleton. `Scene.objects: BTreeMap<ObjectId, SceneObject>` (serde default — old manifests load empty); `SceneObject { id, name, asset, keys: Vec<ObjectKey> }`, where the asset must be a `ModelObj`/`ModelFbx` (the `AddObject` command rejects other types). `ObjectKey { frame, position, yaw, pitch, roll, scale }`: yaw is primary, pitch/roll/scale are optional in the manifest (default 0/unity); number finiteness and a positive scale are validated before applying.

An object's transform at a frame is a pure function `evaluate_object` (pose-style, shared by the renderer, the GUI and tests): position and scale are linear, angles take the shortest arc, outside the key range it holds, and an empty track keeps the source transform. The `AddObject`/`RemoveObject`/`SetObjectKey`/`RemoveObjectKey`/`ReplaceObjectMotion` commands are atomic with a scene snapshot, an undo step and a revision bump. Rendering: forge spawns the object root with the model's parts/materials through the shared loading path; a skinned model renders in bind pose with no clip and no outline; `apply_scene_frame` sets only the root transform. Surfaces: Session Ops and MCP (`object_add`/`object_remove`/`object_key_set`/`object_key_remove`, listed in `state_get`), CLI (`add-object`, `set-object-key`), GUI (an object outliner with minimal key editing).

## Import and assets

The ufbx adapter normalizes axes, units (meters), hierarchy, bind matrices, weights, materials and tracks. Internal coordinates: a right-handed system, Y up. Material and influence-count limits are checked explicitly; invalid data is not silently turned into a static model.

Verified by a build on the CC0 KayKit rig (a mixamo-like path; literal Mixamo files were not tested). Fixed importer invariants: the skeleton is assembled globally across all skinned meshes in the file (a character may have several meshes on one skeleton); vertices are baked into one shared bind-pose world via geometry_to_world, and inverse bind comes from `cluster.bind_to_world` (not geometry_to_bone — that depends on the space of the specific mesh); the bones' rest pose is derived from the bind matrices, not from the current node local transform.

Animation is no longer part of import. An imported rigged model is **static**: it stands in bind pose, moves as a prop and has no poses. Import of animation stacks, clip sampling at 24 fps, skeleton compatibility checks, clip-use tracks, blending, root motion and profile retargeting are removed from the program together with `core/clips.rs`, `core/retarget.rs` and their runtime part. The single consumer of `AssetKind::MotionFbx` went with them; the variant remains only so that old manifests can be read.

Implemented (materials P0): OBJ/FBX import with materials per mesh part. `ModelData` carries a `MaterialRecord` table (base color sRGB + texture, metallic/roughness, normal map; serde default — old data loads with an empty table) and a partition of the `parts` index buffer by material with no gaps or overlaps; the vertex/skin arrays are shared and the outline is one combined hull. Reading: `pbr.*` from ufbx with a fallback to `fbx.*`, OBJ-MTL via `load_external_files` (Kd/map_Kd/Pr/Pm/norm). A triangular face is not passed to `ufbx::triangulate_face_vec` (version 0.4 returns an empty index list for it) and keeps its three indices directly; an n-gon goes through the triangulator. That is why a static OBJ cannot be "visible in the document but with no primitives on the GPU". Rendering: one Mesh3d entity per part, material is a StandardMaterial; the base-color texture is decoded as sRGB, normal and metallic/roughness are linear; separate metallic/roughness maps are packed on the CPU into G=roughness/B=metallic with neutral 255 channels, and a matching combined map is treated as the glTF layout; spec/gloss files (roughness_as_glossiness) invert the factor and the G channel; tangents are generated for normal-mapped parts. Texture paths are resolved inside the project root (canonicalization, refusal to escape), and an unavailable texture is a warning plus the factor. Unsupported features (layered/procedural textures, heightmap bump, per-map UV transforms) are explicit diagnostics in `ModelData.diagnostics`/a render warning, not a silent white mesh.

Model import is bundled: the CLI import, the GUI import button and the Session Op::AssetImport put the OBJ/FBX together with its MTL and textures into their own bundle directory `assets/<name>[-n]/`, preserving the relative layout, so the bundle is self-contained after the source is deleted. Every dependency path is canonicalized and must stay inside the source directory; escaping via `..` or a symlink rejects the whole import (the half-assembled directory is removed). Limits: ≤64 dependency files, ≤256 MB total, textures ≤8192px. Textures embedded in an FBX are extracted to the bundle root; missing ones are a diagnostic, not a rejection.

### Camera (corrective_2 C1/C2)

A camera key (`TransformKey`, shared by every scene camera) carries, besides the pose and angles, optional `roll` (horizon tilt), `look_at` (aim point), `focal_mm` (focus on the key) and `ease` (segment curve); all are serde default, so old manifests load unchanged. `look_at` overrides a given yaw/pitch: the direction is computed with the renderer's basis (`YXZ(yaw, pitch)`, looking down local −Z), so the frame matches what the camera sees and the agent needs no trigonometry for orbit/follow. The single interpolation point is `Camera::sample`, returning `CameraPose {translation, yaw, pitch, roll, focal_mm}`; both the renderer and the pure diagnostics use it, so coverage always matches the frame, including a zoom inside a camera range. Interpolation behavior: the segment fraction is shaped by the starting key's `KeyEase` curve (`linear|ease_in|ease_out|ease_in_out`, cubic with no new dependencies), yaw takes the shortest arc (the previous linear interpolation took a turn from 170° to −170° "the long way"), focal length interpolates linearly, and a key without its own `focal_mm` takes the camera's base focal length. The `Command::SetCameraKey` command checks pose/angle/roll/target finiteness and a positive focal length before mutating, and the "camera looks at the scene" rule after; `SetCameraFocalKey` does not touch the pose and does not check the rule. Surfaces: MCP `camera_key_set` (the `camera` parameter; without it — the active camera; `look_at`, `roll`, `focal`, `focal_preset`, `ease`), `camera_focal_key_set` (a zoom without changing the pose: at a frame without a key the pose is sampled from the track, so a zoom can be placed anywhere inside the range, and the frame rule does not apply to it), `camera_lens_set` (the base lens); CLI `set-camera --roll --look-at --ease --focal`. Lens presets (`ultrawide 16 | wide 24 | normal 35 | portrait 50 | portrait_tele 85 | tele 135 | super_tele 200`) are accepted by the `focal_preset` field; an unknown name is `invalid_input`, not a silent default.

### Cameras as scene entities

There is **one way to make a camera** in a scene: `Scene.cameras: BTreeMap<CameraId, SceneCamera>`. `SceneCamera { id, name, range, camera, target }` — a name, its own range inside the scene, an ordinary `Camera` (keys + base lens) and an optional attachment to a subject. The old `scene.camera` and `scene.shots` are gone from the document: camera 0 (`SCENE_CAMERA`) is the scene's own camera, which is where a legacy `camera` field lands on load, and every former shot becomes a camera with the same id (the old `shots` field is read as `cameras`). `normalize_legacy` brings a loaded document to the "camera 0 always exists" invariant, `Scene::new` creates it right away, and `Scene::camera_for(None)` returns exactly it. A film clip references a camera (`FilmClip.camera`, serde alias `shot`).

**The active camera** lives in the document (`Scene.active_camera`), not in the session: a render without a camera uses it, the viewport shows it too, and the same project file renders identically from any session. `AddCamera` makes the new camera active, removing camera 0 is refused (it is the fallback), `ActivateCamera` selects explicitly, and removing the active camera falls back to camera 0.

**Attachment to a subject** is `CameraTarget { mode, subject }`, where the subject is a scene actor or object and the mode is one of two:

- **Track** (`track`): the camera stands where its keys put it and only turns to keep the subject in frame; its position does not change.
- **Follow** (`follow`): the camera is attached to the subject — its keys are read in the subject's frame (position, angles and aim point alike), so it travels and turns with it, like a third-person view. A key with `look_at` at a local point (say `[0, 1.2, 0]`) always keeps the subject in frame; a key without `look_at` is a rigid attachment. Only the subject's yaw is carried over: tilting a prop does not roll the camera's horizon.

A subject that is gone (deleted, or in a hand-written document) does not break the attachment: the camera falls back to its own keys in world space — deterministically and without a crash — and `validate` reports `camera_subject_missing`.

**The "camera looks at the scene" rule** is enforced in core, at the command layer (`SetCameraKey`, `SetCameraTarget`): a camera standing **inside the scene volume** counts as seeing the whole scene (100 %) — by decision, an interior camera is not punished for seeing only part of a big box; otherwise the fraction of the scene volume inside the frame pyramid is computed on a regular 5×5×5 grid of points, and below `MIN_SCENE_IN_FRAME` (20 %) the command is refused with the code `camera_faces_away`, its `details` carrying `camera`, `frame`, `scene_fraction` and `minimum` — the agent sees a number it can work with. Changing the lens and the focus is **not** checked by the rule: a zoom is a framing choice, not a direction (a long lens outside the box legitimately sees a small part of the volume).

The pure part of the camera lives in core and is tested without a GPU: `camera::camera_pose` (the camera's world pose with the attachment applied), `camera::scene_in_frame` (the rule and the fraction), `camera::subject_transform`/`subject_aim` (the subject's pose and aim point), `view::Frustum` (the frame: `from_pose`, `contains`) and `view::DEFAULT_ASPECT`. The renderer, the commands and diagnostics all use the same `camera_pose`, so the frame, the coverage number and a refused key all talk about the same frame; `Renderer::render_frame`, `apply_scene_frame` and `LiveSync::apply` take a camera id and the project.

Surfaces: MCP `camera_add`/`camera_remove`/`camera_select`/`camera_range_set`/`camera_key_set`/`camera_key_remove`/`camera_lens_set`/`camera_focal_key_set`/`camera_target_set`/`camera_get`/`camera_report`, and a `camera` parameter on `render_scene`/`render_still`/`film_add`/`look`/`camera_coverage`/`background_fit`; CLI `add-camera`/`camera-select`/`camera-target` and `--camera` on the render and the film; GUI — a cameras panel with the list, the active one, the range, the lens, the keys and a target picker. The `shot_*` tools are gone.

Deliberately deferred: deterministic camera shake, motion presets (dolly/pan/crane/orbit/follow/handheld), and aperture/depth of field — the first two need a separate decision about data shape, and the available set of Bevy 0.17.3 crates has no suitable DoF component (see the bloom/vignette decision).

### Metric prop catalog (corrective_2 K1/K3)

`phantom_core::catalog` — one `CATALOG` table instead of verbal agreements: each entry has a name, a section (`primitive|furniture|interior|animal|street|exterior`), full dimensions in meters, an origin (at base center — the item stands on `y = 0` rather than sinking into the floor), named material groups (matching `target` in `material_set`) and a hint for the director; interiors additionally have `open_sides` (walls that are not built: the camera's side does not block the frame), `openings` (doors) and `furniture` (the room's furniture set); on the others those are empty. Runtime builds the geometry (`props::prop_model`) procedurally from this table — no external files and no licensing questions; tests compare the generated mesh's dimensions against the table, check that the material partition has no gaps, and check that a cut-out wall really is not built. Sizes in JSON are rounded to a millimeter (`builtin::mm`): the table stores f32, standalone and bridge serialize f32 differently, and without rounding the same catalog would look like different numbers. A scene object gained `builtin: Option<String>` (serde default — old manifests load as before): with a name given, the mesh comes from the catalog, no asset file is needed, and every existing mechanism (transform keys, bone attachment, material patches) works unchanged. Surfaces: MCP `catalog_query {kind?, query?}` (search by section and substring), `prop_add {scene?, name, prop, pos?, yaw_deg?, pitch_deg?, roll_deg?, scale?}` and `prop_grid {prop, rows, cols, origin, step?, gap?, prefix?, yaw_deg?, scale?}` — a row or grid of props in **one atomic package** of `AddBuiltinObject` (one undo step, one revision, the stage clamp applied to every item, the answer carries the created ids and `clamped`), where the default step comes from the prop's own size times `gap` (1.2 by default) and an explicit `step` in meters overrides it; CLI `catalog [--kind] [--query]`, `prop-add` and `prop-grid`; `builtin_catalog` additionally returns `props`, `human_roles` and `animal_heights_m`. An unknown name is `not_found` with `details.hint = catalog_query`, an unknown section is `invalid_input`.

**The library sections.** `animal` — static animal figures: props, not actors. An animal has no skeleton and no skeletal animation; a "walking dog" is made with the object's own transform keys, and the pose (stand/sit/lie) is a separate catalog entry — a variant exists where it reads in frame. An animal is drawn from proportion parameters (body, head with ears and a snout, four legs, a tail) in one function, not a copy of code per species. `street` — outdoor items; for the ones where it matters, the orientation is fixed and stated in the hint (a streetlight lights toward `+Z`, stairs ascend along `+Z`, a car is long along `Z`) — yaw stays the only way to turn a prop. `exterior` — outdoor grounds (yard, park, crossing): a flat ground with no walls and no ceiling, the slab hanging below `y = 0`, so the top of the ground is `y = 0` and props and cameras are placed on it exactly as on an interior floor.

**A room arrives as a package.** A furnished room's `furniture` is a list of pieces with an offset in the room's own frame, its turn (degrees on the wire) and its height: a monitor stands on a table rather than under it, a picture on a wall. `prop_add` of such a room creates the shell plus one object per piece: one undo step, one revision, and every piece is still an ordinary scene object that can be moved, turned and deleted on its own. The package is expanded in the command layer (`AddBuiltinObject`) rather than at the MCP boundary: GUI, CLI and agent must produce the same package, and the history must never be able to hold half a room. The offsets are computed from the shell's key **after** the stage clamped it — otherwise a room placed past the boundary arrived with its furniture outside through the wall. `prop_grid` refuses a furnished room: a grid is for single props, and a package inside a package is several rooms and dozens of objects under one undo step. The answer carries every created id under `objects`.

**The clamp stays quiet about noise.** The stage reports a corrected coordinate only when the shift exceeds 0.1 mm: rotating the footprint's own offset produces float noise around 1e-7 m, and without a tolerance every rotated prop would tell the director its coordinate had been fixed.

The proportion table (K3) is the same source of truth: `HUMAN_ROLES` (child/teenager/adult/elderly: height, eye, shoulder, hip, knee) and `ANIMAL_HEIGHTS` (builtin actors). Adult height stays 1.74 m — a product decision, and props are built in meters. The horse in the table is above human shoulder height (1.62 vs 1.43) — the edit was made upward, as the report's author asked.

A project is a directory with a JSON manifest, source/created assets, and a separate recoverable cache. Import copies allowed assets into the project; references are relative. Sources are kept; normalized mesh/clip and previews are derived data. Saving first writes the new assets, then atomically replaces the manifest; a crash never leaves a manifest referencing unwritten files. An unknown newer schema version is not overwritten. A missing asset is flagged and blocks the export that depends on it, but not the opening of the remaining data.

Existing `.blend` files, OBJ, images and bakes in the repository are not automatically considered licensed bundle assets. The builtin set needs its own provenance and an explicit license; imported Mixamo files are not redistributed with the app.

## Rendering, background and projections

One GPU renderer serves the viewport and offscreen export without winit/a window. Without a suitable GPU, editing stays available and an image request returns a diagnosable error; a CPU renderer is not promised.

**The background is flat.** The arc screen is removed from the program entirely. The screen is a `width × height` rectangle at `center`, facing the camera's side (+Z): `mesh_gen::screen_mesh` builds four vertices and two triangles, and the `BackgroundFit` UV modes (`cover`/`contain`/`stretch`) compute proportions from the `width / height` ratio. The frame's aim point is the same in the renderer and in diagnostics, so coverage always describes the plane that is actually drawn.

Implemented: `Background { image, width, height, center, fit }`; an old manifest with an arc is read through `BackgroundInput` (`TryFrom`) — the flat screen gets the arc's horizontal length `arc_radians × radius`, and the bulge direction (`Bulge`) is accepted and discarded. `Background::validate` checks positive width/height and a finite center; `SetBackground` calls it before mutating. The image's 3×2 zones are laid out along the screen width and feed ambient and the point sources, identically in preview and export. `camera_coverage` returns `width`/`height`/`center`, the screen's span seen from the camera and `gap_deg`; `background_fit` computes the minimum `width`/`height` that close the frame **on the current screen plane**, and returns `size_covers: false` with an empty suggestion when the camera is not looking at the plane at all — that cannot be fixed by size, the screen has to be moved. `validate` reports `screen_fov_gap` with `needed_width_m`. A video background is silent: its audio track is not mixed (no separate decision was made on this).

The outline is a separate unlit inverted-hull pass after skinning: the same mesh with flipped cull-mode, vertices offset along their normals in screen space; it is not part of the lit material. Thickness is specified in output pixels. The character mesh requirement is continuous normals on silhouette edges (the builtin rig's normals are rounded), otherwise the outline tears at the faces. Export keeps explicit frame IDs, waits for the requested frame's readback and accounts for GPU latency; one `Readback` is submitted exactly once (the component is removed after submission, the observer lives until `ReadbackComplete`), so deferred GPU map callbacks never write into a closed channel. "Grab the current screen" is not an implementation of per-frame export.

Implemented (light and floor P0): the scene document stores `lighting: SceneLighting` (serde default — old scenes get the default setup) and `floor: Option<SceneFloor>` (serde default `None` — old scenes do NOT gain a floor). The light is a three-point key/fill/rim setup of directional sources with fixed directions (key — the slice's previous direction); the per-source settings are color (linear RGB), intensity (lux), enable, and a `shadows` flag; the 8000 lux key default approximates the previous look. Corrective A1/A2: `shadows` defaults to **false** and serializes as false with old projects — the "skinned mesh + shadow pass" path on Bevy 0.17/wgpu fails with a pipeline validation error (Uint32x4 joint indices are not passed into the shadow stage), so shadows are a deliberate opt-in (`shadow|noshadow` in CLI `parse_light`, `shadows` in MCP PLight) until the skinned shadow pipeline is fixed; enabled light works without shadows. Ambient from the background is no longer a constant: `ambient_from_background` computes a semi-desaturated color (50 % toward its own luma — the background does not tint the actors) and a brightness of `150 + 2000·mean_luma` lux (night ~190, day ~950, bright background ~1750); the zone PointLights were raised from 150 lm (~1–9 lux) to `250_000·(0.25+mean)` lm (hundreds of lux of fill light) — both formulas are pure and covered by unit tests. The shared forge-path camera (viewport and offscreen export render identically) carries LUT-free `Tonemapping::Reinhard`: TonyMcMapface requires the Bevy `tonemapping_luts` feature, which we do not ship, and left the offscreen camera without a valid pipeline. Reinhard adds no new dependency and gives a deterministic working path. The flat screen's material stays unlit; tonemapping does not change its brightness relative to the previous balance. MSAA 4x (`Msaa::Sample4`) sits on the same camera. The floor is a matte (roughness 0.95, metallic 0) opaque plane at y=0 that receives shadows; with the floor off, the PNG keeps full alpha; with it on, the floor is opaque frame geometry (a transparent shadow-catcher is out of P0 scope). The `SetLighting`/`SetFloor` commands validate finiteness and non-negativity of colors/intensities before mutating, are atomic, and undo in one step. Surfaces: Session operations `lighting_set`/`lighting_get`/`floor_set`/`floor_get`, MCP `scene_lighting_set`/`scene_lighting_get`/`scene_floor_set`/`scene_floor_get`, CLI `set-lighting`/`set-floor`, and a "Light and Floor" panel in the GUI. Changing light/floor are ordinary document commands: they bump the revision and rebuild the GPU world through LiveSync.

Bake keeps transparent PNG projections plus camera, range, resolution, and dependency-revision metadata. Changes to pose, camera, materials, light, or an influential background invalidate the bake. For correct occlusion between several Phantoms and objects, the main final render uses the shared depth of the original 3D scene; the separate PNGs are derived layers, not a replacement for the depth buffer. Viewing baked projections is possible from a matched camera; an arbitrary new camera requires re-baking. Neither export nor toggling the view deletes the sources.

## Three drawing kinds

2D drawings are frames/exposures of raster layers in output coordinates. 3D strokes are points with thickness, color, and visibility time in scene coordinates, rendered as geometry. Drawings and Phantoms are not merged into one rig.

Implemented (2D): the document stores strokes (points, color, thickness, eraser mode), not pixels — the exposure raster is derived; one brush gesture = one command = one undo. The layer canvas is fixed (1920×1080) and scaled to the output resolution. An exposure holds until the next one; onion skin ±1 exposure is viewport-only. Compositing: offline — CPU over the readback buffer; live viewport — unlit quads in front of the camera with a texture cache keyed by stroke version.

Model paint uses hits against the visible deformed surface, barycentric UV, and writing the brush into a separate editable base-color texture. Texture tile changes form one undo operation. UV seams, overlapping UVs, and picking agreement with skinning each need separate verification: we do not promise seamless painting merely because raycast exists. Missing UVs must be diagnosed rather than writing into a random region. Auto-unwrapping is not the chosen solution.

## Film, audio, and media processes

A film is ordered references to scene ranges and the camera that shot them, with no transitions. One film-time-to-scene-time mapping function is applied to both image and sound. Audio clips belong to a scene or to the film; a scene's audio is trimmed together with its range and is not mixed a second time at film level. The core mixer sums float PCM with volume/mute; preview and export use the same logic. Values are clamped to range before integer output; clipping is shown to the user.

Implemented (no audio): `FilmClip { id, scene, range, camera }` in the document, `film_map` — the single time mapping; MP4 video-only by streaming frames into ffmpeg's stdin; AAC comes with the audio step without changing the pipeline. There is no film preview in the viewport — export only.

Implemented (cameras in the film): a scene camera is an ordinary document entity (see "Cameras as scene entities"), so the edit references it rather than a separate "shot". `FilmClip.camera: Option<CameraId>` (serde default `None` — the scene's active camera): a clip references a range of the scene shot with the chosen camera; a named camera's clip range must equal its range (`AddFilmClip`/`SetFilmClipRange` validate), while camera 0 covers the whole scene and takes any range. A clip maps into its scene's range through `film_map`/`film_map_clip`, so the scene's audio is not duplicated; film export renders a frame with the clip's camera. The `AddCamera`/`RemoveCamera`/`ActivateCamera`/`SetCameraRange`/`SetCameraKey`/`RemoveCameraKey`/`SetCameraLens`/`SetCameraFocalKey`/`SetCameraTarget` commands are atomic and undo in one step; `RemoveCamera` also removes the film clips pointing at that camera in the same command, `SetCameraRange` retimes them (undo step `SceneAndFilmReplaced`), and removing the active camera falls back to camera 0. `state_get` returns the scene's camera list with the active marker; the GUI shows a cameras panel.

Implemented (audio): scene and film tracks with volume/mute and clips on frames; the core mixer (mix_frame zeroes, mix_into layers — the contracts were separated after a bug where film tracks wiped scene audio); decoding to f32 48 kHz via ffmpeg; the film mixes its scenes through film_map plus film tracks, and export multiplexes AAC from a temporary WAV; cpal preview with a silent fallback when there is no device (per-frame feeding along the timeline rather than along audio time — a small preview drift is possible, export is frame-exact); a peak >1 is shown as clipping.

FFmpeg is launched by arguments without a shell; input paths and the output directory are validated. Process count, buffers, and probe duration are bounded; cancellation terminates processes and removes temporary files. There is no silent codec download from the network. `ffmpeg`, `ffprobe`, and support for the required decoder/encoder are checked; the binary's presence does not guarantee H.264. For predictable software output the original candidate is libx264 and AAC; when they are missing, MP4 export reports the reason and PNG stays available.

Encoding uses frames and PCM from a fixed range with matching timestamps. The project keeps being edited independently of the export job's snapshot. The result is published only after successful completion, and cancellation does not damage the previous file; existing output is never overwritten without explicit permission.

Selective source reading, not a full audit:
- FilmCraft h264enc/aac have relatively narrow APIs but require a bitstream and a pinned craft-media; a ready synchronous MP4 additionally needs a container and an export adapter. For the chosen external FFmpeg that is extra integration.
- TextureCraft formats/paint depend on core/texel/geom/compose and their mesh/UV/pixels models. Their FBX mesh API does not by itself prove that the rig and animation are preserved. Porting a whole paint editor was not chosen.
- EffectCraft remains a reference for a command-first interface, not a verified character-animation library.

## Implementation status

The first vertical slice "scene → frames" is built and verified (CLI `phantom-animate`, three crates `phantom-core`/`phantom-runtime`/`phantom-animate`). Verified by tests and by running on the available GPU (Vulkan): the project document with commands and undo; an integer 24 fps timeline; the builtin humanoid rig with poses; atomic project storage; OBJ import (tested on a Wolf model); OBJ+MTL material import with two parts, textures, and bulk copying into the project (CPU tests on generated files); headless rendering to PNG with alpha, a flat background, skinning, and an inverted-hull outline with thickness in pixels; deterministic frame time; project round-trip through disk.

On top of the slice sits the storyboarding GUI (`phantom-animate edit`, bevy_egui 0.38.1 + egui 0.33.3 — compatibility with Bevy 0.17.3 confirmed by building and running it): a viewport rendering the scene into a texture, a timeline with keys/scrub/play, an outliner, stage and background panels, and the pose combo in the key row. The live world is persistently synchronized with the document (LiveSync): structure is rebuilt from the revision counter, and only transforms change per frame. PNG export from the window runs as a separate CLI process — GPU isolation and reuse of the proven path. The windowed egui integration needs a separate window camera (Camera2d): without it the primary egui context attaches to the scene camera and draws the interface into the viewport texture.

Implemented additionally: per-frame 2D drawing over the frame (one layer in the UI, the model is a list of layers; brush/eraser/color/thickness, exposure keys, onion skin ±1, the drawing lands in the export); film assembly (reference clips, reordering, trimming) and MP4/H.264 video-only export through external FFmpeg with a libx264 check, a temporary file, and cancellation; an MCP server (rmcp 3.8, stdio) in two modes — a standalone session without a window and a bridge to the open editor (newline-JSON Unix socket in a 0700 directory, a lock file holding the socket path, refusal to a second writer), named typed tools over the shared Session/Op dispatcher, and render jobs as child CLI processes with job ID/progress/cancellation.

### Durable project-lock contract

Standalone `Session` and the GUI bridge use the same `.phantom.lock` record and guard. A current record contains a format version, PID, Linux process-start identity when `/proc` provides it, an unpredictable ownership token, optional bridge socket, and heartbeat timestamp (filesystem mtime is also reported). Acquisition is exclusively `create_new`; no `exists`-then-write path is permitted. Release and `Drop` reread the token and therefore never unlink a replacement owner. The GUI acquires before binding its Unix socket and drops the guard if bind fails. `project_new` acquires before manifest creation and drops the guard on creation failure.

A PID is live only when `/proc/<pid>/stat` exists and, when recorded, its start identity matches; a missing PID or reused PID is definitely dead and may be reclaimed with warning data. A tokenless legacy lock is reclaimed only for a definitely dead PID. Parse failures, inaccessible process state and non-local/ambiguous ownership are not silently removed; `force` is required, and even force never removes a definitely live lock. Bridge lock reads expose PID live/dead/ambiguous status and socket presence for diagnostics. `lock_release` reports the observed owner; a lock already owned by the calling session is an idempotent no-op.

A `Session` owns at most one guard. Reopening the same canonical directory returns `already_open: true` without reacquisition. Switching that Session to another directory is rejected (rather than risking unsaved state or stranding the old guard); clients create another MCP session to switch projects.

Extending MCP to the core commands (production access, stage 1): `state_get` also returns the Phantoms (id, name, rig kind, key count), the film (clip id, scene, range, camera), scene stages and the scene and film audio tracks (id, name, volume, mute, clip count). Core commands previously unavailable to the agent are wired up as operations and MCP tools under the same names: `scene_range_set`, `camera_key_remove`, `phantom_remove`, `motion_key_remove`, `motion_replace` (batched ReplaceMotion — one undo step), `background_clear`, `audio_track_remove`, `exposure_remove`, `layer_add_2d`. The internal Session/bridge `Op::MotionReplace` keeps the legacy tuples and a parallel `yaws` for serialization compatibility, but the MCP boundary accepts only typed motion objects with `pose` and `yaw_deg` inside each key. `background_set` takes `video`/`width`/`height`/`center`/`fit`, with serde defaults 24×8 m at [0,4,−5]. History is available to the agent: `history_undo`/`history_redo` (applied=false on an empty stack) and `history_list` (stack depths + names of the most recent operations). `render_film` takes a `frames` range and passes it through into the child CLI job's arguments. All operations go through the shared Session/Op dispatcher, so the standalone stdio mode and the bridge to the window receive them at the same time.

Stage 2 (corrective C3/D2–D4) adds queries and service tools: `camera_get`, `asset_get`, `film_get`, `project_recent`, `job_wait`, `describe` (see "Commands and MCP"). ## Architecture verification

Before any claim that this works we need: the same pose and position under direct seek and sequential playback; an offscreen PNG with outline and alpha; GUI/MCP parity; a project round-trip; export cancellation without corrupting files; movie cuts with audio and no drift; UV painting on a deformed model; failure without a GPU/codec, and MCP being barred from escaping the permitted root.

These are verification criteria, not tests already passed. Achievable speed, support for a specific Linux GPU/driver, the range of FBX materials, and the quality of the starter motions are unconfirmed. The architecture does not introduce network synchronization, universal retargeting, or a custom media codec as a way to hide these risks.

## Bundled procedural actors

`RigRef::Builtin` keeps its legacy JSON string representation and humanoid skeleton. `RigRef::BuiltinActor { actor }` adds explicit `Humanoid`, `Child`, `Teen`, `Elder`, `Wolf`, `Horse` and `Bird` profiles. Childhood and old age are not a separate rig and not a second set of poses but a proportion profile of the same humanoid skeleton: `human_role()` maps an actor to a `HUMAN_ROLES` row (`adult|child|teen|elder`), and height, eye level and limb length come from there. A child is not a shrunk adult: its legs are short relative to its torso, so the proportions are scaled per region (hips, torso top, crown) rather than by one factor; the adult stays the identity scale, and its geometry did not change when the roles appeared. Geometry and skeletons are built locally from original primitives and are licensed by `BUILTIN-ACTORS-LICENSE.txt` (MIT, including generated assets); unrelated repository assets are not bundled.

**Poses instead of actions.** An actor holds a pose: `ActorPose { Stand, Sit, Lie }`, and the species declares its own set — the human and the wolf hold all three, the horse stand and lie, the bird stand and sit. `rig::sample_actor_pose(actor, pose)` is static and takes no time; the pose is taken from the key in force and switches on its frame. The human `Sit` (hips at 0.45 m, thighs forward, shins down) and `Lie` (the body turns about the hips and lies on its back) are drawn separately. An unavailable pose is rejected by the commands (`unsupported_pose`) and diagnosed during scene construction; pure evaluation of an externally corrupted document falls back to the default pose. The footprint for clamping to the stage depends on the pose.

Profile skeletons are shared by timeline evaluation and rendering, and the mesh/skin caches are keyed by actor profile. Coordinates are Y-up, metres, forward +Z. A motion key carries yaw about +Y in radians (serde defaults it to zero), and position and yaw must be finite on deserialization, in the commands and during scene construction; yaw follows the shortest arc deterministically, while position and pose are pure functions of the frame. Imported rigs also get the root yaw, but they have no poses: they render in bind pose.

Actor and pose names are shared by the GUI, CLI, MCP and session dispatch through one catalog (`crates/app/src/builtin.rs`): the GUI picks an actor from a combo and filters poses in the key row; CLI `add-phantom --rig` accepts `builtin` (legacy), `humanoid|child|teen|elder|wolf|horse|bird` or an asset ID, and `set-key --pose` accepts every catalog pose; MCP `phantom_add` takes an optional `rig_actor` (conflicting with `rig_asset`, which is preserved unchanged), `builtin_catalog` returns profiles with poses and a default pose, and `key_set`/`motion_replace` accept every catalog pose. These are simple stylized rigid-weight low-poly models with static poses, not realistic anatomy, locomotion or contact physics.
